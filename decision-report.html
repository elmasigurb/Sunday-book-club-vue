The requested explanation

How the backend affected UX & UI.

The backend was not an invisible plumbing change. It changed what the interface could promise, what states it had to show, and how much trust users could place in every action.

Before · static showcase

A page to read

  • Fixed book and review arrays
  • One long-scroll destination
  • Calls to action without durable member state
  • No network waiting or failure states
  • The same experience for every visitor
→

After · connected platform

A club to participate in

  • Live catalogue, meetings and community content
  • Searchable, linkable book and event pages
  • Personal shelf, reviews, profile and RSVP history
  • Loading, empty, success, waitlist and error feedback
  • Authenticated UI adapts to ownership and session state
More useful UI

Persistent data unlocked catalogue search, book detail pages, event pages, personal shelves, member statistics and editable reviews.

More interface states

Async data introduced loading, retry and empty designs. Authentication introduced signed-in, signed-out and session-checking states.

More precise language

The interface can distinguish registered, waitlisted, cancelled and attendance-confirmed instead of showing one vague RSVP message.

Safer actions

Verified ownership lets edit and delete controls appear only where appropriate; capacity checks make “Save my spot” truthful.

Better continuity

A returning reader sees their own shelf and activity. The product remembers decisions between visits rather than resetting every time.

A real trade-off

The UI is more capable but depends on network and service health. The new feedback states and retry paths are the design response to that cost.

Hard topics, plainly

Technical ideas without the fog.

Open a topic for a short explanation of the concepts that carry the most architectural or security weight.

What is Row Level Security?

RLS is a database rule that decides which rows a user may read or change. Even if application code makes a mistake, the database can still refuse access to somebody else’s profile, shelf, review or registration.

Why PKCE for a magic link?

PKCE connects the sign-in attempt started in this browser with the callback that completes it. It reduces the risk that an intercepted authorization result can be reused elsewhere, while keeping sign-in passwordless.

Why both constraints and validation?

Zod validation gives fast, friendly API errors. Database constraints are the final guarantee when requests race or another trusted tool writes data. One improves feedback; the other protects truth.

Why can’t the browser write RSVPs directly?

Seat allocation needs one trusted capacity check. If every browser could update RSVP rows directly, a modified request might bypass the waitlist or change organizer-only attendance fields.

What does “additive migration” mean?

Instead of rebuilding the database, the migration adds columns and tables, fills required values for existing rows, then adds stricter rules. That keeps earlier content and registrations intact.

Why does history-mode routing need a rewrite?

A route such as /books/apricot-skies belongs to Vue, not to a physical server file. Production hosting must return index.html for unknown page routes so Vue can render the right screen.
